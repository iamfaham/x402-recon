# Ledger v0.1b Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Stop the tool presenting a service grouping as confident payer identification, by splitting the cascade into two independent axes scored against separate answer keys.

**Architecture:** Eight tasks. Vocabulary and schema first (a transaction now carries one categorization *per axis*), then the cascade splits into independent payer and service passes, then the simulator and ingest grow a second ground-truth file, then report and evaluate learn about both axes. The final task runs the measurement.

**Tech Stack:** Python 3.13+, stdlib only (`sqlite3`, `csv`, `json`, `random`, `argparse`, `dataclasses`, `datetime`, `decimal`, `collections`, `pathlib`), `pytest` as the sole dev dependency, `uv` for environment management.

**Spec:** `docs/superpowers/specs/2026-08-19-ledger-v0.1b-design.md`

## Global Constraints

- **Python:** `requires-python = ">=3.13"`. Runtime dependencies MUST remain empty — stdlib only. `pytest` is dev-only.
- **Money:** amounts are ALWAYS integers in micro-USDC. Never a float. A refund is a **positive** amount with `tx_type='refund'`.
- **Timestamps:** ISO 8601 UTC, `YYYY-MM-DDTHH:MM:SSZ`, zero-padded, stored as TEXT.
- **Never force a bucket; never silently drop.** Rejected rows are counted and surfaced with reasons.
- **No tax advice:** no user-facing string may advise on tax or accounting treatment.
- **Pre-registered and immovable:** `TIME_CLUSTER_THRESHOLD = 0.70`, `CALIBRATION_THRESHOLD = 0.95`, `MIN_VERDICT_SAMPLE = 20`. Their *values* do not change in this release. `CALIBRATION_THRESHOLD` changes only in *what it is applied to* — per confident rule instead of the confident tier in aggregate, which is strictly tighter.
- **The service axis claims no confidence.** Its rows carry the `DESCRIPTIVE` tier, never `CONFIDENT`.
- **`time_cluster` is not to be tuned.** Its sample size changes as a side effect of this release. Record whatever it becomes; do not adjust the cascade to reach a sample size.
- **Existing tests:** 149 currently pass. Any change to one must be a deliberate, justified correction recorded in the task report — never a threshold quietly loosened.

### Task 3: Split the cascade into two independent passes

The behavioral core of this release. Today's single `elif` chain means a payment from a recognized sender that *also* carries a specific memo receives only the payer label — the service is discarded.

**Files:**
- Modify: `src/ledger/categorize.py`
- Modify: `src/ledger/report.py` (join filter only)
- Modify: `src/ledger/evaluate.py` (join filter only)
- Test: `tests/test_categorize.py`

**Interfaces:**
- Consumes: `AXIS_PAYER`, `AXIS_SERVICE`, `DESCRIPTIVE`, `CONFIDENT`, `UNCERTAIN`, `UNCATEGORIZED`, rule names from `ledger.models`
- Produces:
  - `categorize_payers(txns, config, categorized_at) -> list[Categorization]`
  - `categorize_services(txns, config, categorized_at) -> list[Categorization]`
  - `categorize_transactions(txns, config=DEFAULT_CONFIG, now=None) -> list[Categorization]` — both passes concatenated, so its length is `2 * len(txns)`
  - `run_categorize(conn, config=DEFAULT_CONFIG) -> int` — returns rows written, now two per transaction

**Why this task also touches `report.py` and `evaluate.py`:** the moment `run_categorize` writes two rows per transaction, their existing `LEFT JOIN categorizations c ON c.transaction_id = t.id` matches **both** rows, doubling every amount in the report and every prediction in the scorer. Adding `AND c.axis = '{AXIS_PAYER}'` to each preserves today's exact behavior. The real two-axis work lands in Tasks 6 and 7; this is only what keeps the suite honest.

```python
def categorize_payers(
    txns: list[Transaction], config: CascadeConfig, categorized_at: str
) -> list[Categorization]:
    """Answer 'who paid this' for every transaction.

    Repetition of a sender address is evidence of identity, so sender_match
    claims confidence. Proximity in time is a guess, so time_cluster does not.
    A shared memo is deliberately NOT consulted here: it identifies a service,
    not a payer, and treating it as identity is what let unrelated strangers be
    reported as one payer.
    """
    sender_counts = build_sender_counts(txns)
    clusters = find_time_clusters(txns, config)

    results = []
    for transaction in txns:
        label, tier, rule = UNCATEGORIZED, UNCERTAIN, RULE_NONE

        if sender_counts[transaction.sender_address] >= config.min_occurrences:
            label = f"agent:{transaction.sender_address}"
            tier, rule = CONFIDENT, RULE_SENDER_MATCH
        elif transaction.tx_hash in clusters:
            label = clusters[transaction.tx_hash]
            tier, rule = UNCERTAIN, RULE_TIME_CLUSTER

        results.append(
            Categorization(
                transaction_id=transaction.id,
                axis=AXIS_PAYER,
                category_label=label,
                confidence_tier=tier,
                rule_matched=rule,
                categorized_at=categorized_at,
            )
        )
    return results


def categorize_services(
    txns: list[Transaction], config: CascadeConfig, categorized_at: str
) -> list[Categorization]:
    """Answer 'what was this paid for' for every transaction.

    Grouping is by exact memo string, which carries an inference - that the same
    memo means the same service - so the result is measured. Until it is, every
    row is DESCRIPTIVE: stated, not claimed.
    """
    memo_counts = build_memo_counts(txns, config)

    results = []
    for transaction in txns:
        label, rule = UNCATEGORIZED, RULE_NONE
        memo = None if transaction.memo is None else transaction.memo.strip()

        if (
            not is_generic_memo(transaction.memo, config)
            and memo is not None
            and memo_counts[memo] >= config.min_occurrences
        ):
            label = f"service:{memo}"
            rule = RULE_MEMO_MATCH

        results.append(
            Categorization(
                transaction_id=transaction.id,
                axis=AXIS_SERVICE,
                category_label=label,
                confidence_tier=DESCRIPTIVE,
                rule_matched=rule,
                categorized_at=categorized_at,
            )
        )
    return results


def categorize_transactions(
    txns: list[Transaction],
    config: CascadeConfig = DEFAULT_CONFIG,
    now: str | None = None,
) -> list[Categorization]:
    """Run both axes. Every transaction gets exactly one row per axis."""
    categorized_at = now or datetime.now(UTC).strftime(TIMESTAMP_FORMAT)
    return categorize_payers(txns, config, categorized_at) + categorize_services(
        txns, config, categorized_at
    )
```

### Task 4: Simulator service ground truth

**Files:**

**Interfaces:**
- Consumes: `UNGROUPABLE` from `ledger.models`
- Produces:
  - `SimulatedBatch` gains `service_truth: dict[str, str]`
  - `write_batch(batch, out_dir) -> tuple[Path, Path, Path, Path]` — now also writes `service_truth.json`

**The service answer key.** Every generated transaction gets a true service:

| Generator | True service |
|---|---|
| Ordinary agent with a specific memo | that memo |
| Ordinary agent with `None` or a generic memo | `UNGROUPABLE` |
| Near-miss pair (`data-feed`) | `data-feed` |
| Rotating-address agent (`invoice-settlement`) | `invoice-settlement` |
| **Memo-drift agent** (`report-api` / `report-api-v2` / `reports`) | **`reporting`** — one service under three names |
| **Shared-memo strangers** (`monthly-usage`) | **`monthly-usage`** — genuinely one service |
| Interleaved one-offs (generic memos) | `UNGROUPABLE` |
| Refunds | the same service as the payment they reverse |

Two of these carry the release's whole argument:

- **Shared-memo strangers** score *correctly* on the service axis. Six unrelated payers really were buying the same service. That grouping was never wrong — it was only wrong when reported as a payer identity.
- **Memo drift** becomes the service axis's adversarial case. One service under three memo strings means exact-string matching will fragment it and lose service recall. That is the measurement doing its job, not a defect to fix here.

    """Render one breakdown row.

    The [needs review] marker is gated on UNCERTAIN specifically rather than on

    """Confident rules whose own precision falls below the threshold.

    The gate is per-rule rather than an average across the confident tier. An

```markdown
## What the two axes mean

Ledger answers two separate questions about every payment, and keeps them
separate on purpose.

**Who paid you** groups by sender address. A sender that repeats is evidence of
one payer, so those groupings claim confidence.

**What they paid for** groups by the memo the payer sent. These groupings
describe what was bought - they are *not* a claim about who bought it, and they
claim no confidence at all.

Earlier versions collapsed both into one "category", which meant several
unrelated payers who happened to buy the same service were reported as one
payer under "Confidently identified". Separating the axes is what fixed that.

## Ground truth format

`evaluate` needs to know the correct answers. Two files, each optional and each
answering one question.

`ground_truth.json` maps a transaction hash to the payer it truly came from:

```json
{"0xabc...": "acme-corp", "0x123...": "__ungroupable__"}
```

`service_truth.json` maps a transaction hash to the service it truly paid for:

```json
{"0xabc...": "weather-api", "0x123...": "__ungroupable__"}
```

Group and service names are arbitrary labels - any stable string. Use
`__ungroupable__` when a transaction genuinely belongs to no group: a one-off
payer never seen again, or a payment whose memo names no real service. Those
are excluded from coverage scoring, because failing to group them is correct.

Supplying only `ground_truth.json` is normal. The payer axis is scored and the
service axis is reported unscored.
```
