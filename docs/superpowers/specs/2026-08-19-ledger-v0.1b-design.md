# Ledger v0.1b — Design

**Date:** 2026-08-19
**Status:** Approved for implementation planning
**Predecessors:** `2026-08-18-ledger-v0-design.md`, `2026-08-19-ledger-v0.1a-design.md`

## Purpose

v0.1a's adversarial simulator caught a real defect the moment it became able to:
`memo_match` measured B-cubed precision 70.6% while its output was counted as **confident
payer identification**. The report currently tells a business owner that five unrelated
one-off payers are one payer, under a heading reading "Confidently identified".

v0.1b fixes the conflation that caused it. The tool has been collapsing two different
questions into one answer.

This tool still only reads and summarizes transactions a business has already received. It
never holds or moves funds, and it does not provide tax or accounting advice.

## The diagnosis

The cascade already knew these were different kinds of thing — it labels them differently:

```python
label = f"agent:{transaction.sender_address}"   # sender_match -> an identity
label = f"service:{memo}"                       # memo_match  -> a service
```

Both were then tiered `CONFIDENT`, and the report summed both into "Confidently
identified", which a reader takes to mean *we know who paid you*.

So `service:monthly-usage` grouping six unrelated payers is not a wrong grouping. Those six
payments genuinely were for the same service. It is a **correct service grouping presented
as a payer identity**. The 70.6% was never measuring how often `memo_match` errs; it was
measuring how often a service grouping fails to also be a payer grouping — the wrong
question to ask of it.

The original project brief asked for three axes: *"which agent/customer, which service was
paid for, which time period"*. v0 collapsed them into a single category field, and that
collapse is what produced this.

## Scope

**In scope for v0.1b:**

- Splitting the cascade into two independent axes, payer and service
- A schema that stores one categorization per transaction *per axis*
- Service ground truth and per-axis scoring
- A per-rule calibration floor replacing the aggregate gate
- A report with separate payer and service breakdowns

**Explicitly out of scope:**

- Smarter service matching (normalization, fuzzy similarity). v0.1b measures exact-string
  matching first and lets the number decide whether more is warranted — the same discipline
  v0.1a applied to `time_cluster`.
- A confidence claim on the service axis. It reports descriptively until measured.
- The third axis from the brief (time period). The schema must not preclude it.
- Real transaction data, and report readability work. Both await customer validation signal.

## The two axes

**Payer axis** — "who paid you":
`sender_match` (confident) → `time_cluster` (uncertain) → `none` (uncategorized)

**Service axis** — "what they paid for":
`memo_match` (exact memo string) → `none`

They run as independent passes, not one ordered chain. A transaction may have a known payer
and a known service, either, or neither.

This is a behavioral fix, not a refactor. Today's single `elif` chain means a payment from a
recognized sender that also carries a specific memo receives **only** the payer label — the
service is discarded. Splitting the passes is what recovers it.

### Consequence: `time_cluster` reopens

`memo_match` leaves the payer cascade entirely, so the transactions it used to intercept now
fall through to `time_cluster` and `none`. `time_cluster` fired on only 2 payments in v0.1a,
below `MIN_VERDICT_SAMPLE = 20`, so its verdict read INSUFFICIENT DATA. With more
transactions reaching it, it may now clear that gate and produce a real verdict against the
pre-registered `TIME_CLUSTER_THRESHOLD = 0.70`.

**Record whichever happens.** Do not tune the cascade to reach a sample size, and do not
adjust either threshold.

## Storage

`categorizations` gains an `axis` column; its primary key becomes `(transaction_id, axis)`.
Idempotent re-runs continue to work through `INSERT OR REPLACE` on that composite key.

Chosen over parallel columns (`payer_label` / `service_label` / …) and over a second table
because it is the only shape where adding the brief's third axis costs nothing. Parallel
columns bake the axis count into the schema and duplicate the tier and rule vocabulary
across column names; a second table means two near-identical tables that drift apart.

The report pays one extra join for this, which is cheap.

Schema version increments, and the existing guard refuses a stale database with an
actionable message rather than migrating.

## What each axis may claim

**The payer axis keeps its tiers**: `sender_match` confident, `time_cluster` uncertain,
`none` uncategorized.

**The service axis makes no confidence claim in v0.1b.** Exact-string grouping *feels*
factual, but scoring it concedes there is an inference inside it — "same memo string implies
same service" — and the memo-drift hazard already generates a case where that inference
fails. So service groupings are presented descriptively, as *grouped by the memo the payer
sent*, with their measured accuracy reported separately. If the number earns a confidence
claim, a later release can make one.

This is the same discipline v0.1a applied to `time_cluster`: do not assert a confidence
level before measuring it.

### The tier vocabulary gains one value

`confidence_tier` is NOT NULL, so service rows need a tier. They take a third value,
`DESCRIPTIVE`, alongside `CONFIDENT` and `UNCERTAIN`. It means *this grouping is stated, not
claimed* — the row records how the grouping was formed without asserting how far to trust it.

`DESCRIPTIVE` is deliberately distinct from `UNCERTAIN`. Uncertain means the tool guessed and
knows it might be wrong; descriptive means the tool is not guessing at all, only reporting
what the memo said. Collapsing them would tell a reader the service axis is unreliable, which
is not what is being claimed either.

The per-rule calibration floor applies only to rules carrying `CONFIDENT`. Descriptive rules
are measured and reported, but a threshold they were never asked to clear cannot warn about
them.

## The calibration gate becomes per-rule

`CALIBRATION_THRESHOLD = 0.95` stops applying to the confident tier **in aggregate** and
starts applying to **each confident rule individually**. The warning fires when any single
confident rule falls below it.

The value does not change. Reusing it rather than pre-registering a new number avoids
choosing a threshold after seeing the result it will judge, and the change is strictly
tighter than what it replaces.

This is the structural fix. The aggregate gate let `sender_match`'s 106 payments at 100%
precision dilute `memo_match`'s 17 at 70.6%, so the confident tier read 95.9% and passed. A
gate that a 70% rule clears by dilution is a gate with a hole in it. The hole is the
averaging, not the particular rule that fell through it — and it would return the moment a
second confident payer rule exists.

At seed 42 the payer axis has one confident rule at 100% precision, so it passes cleanly.
The 70.6% stops being a failure and becomes a service-axis measurement, reported against the
right answer key with no confidence claimed on it.

## Ground truth

A second file, not a richer one. `ground_truth.json` keeps its exact current shape —
`tx_hash` to payer group — and `service_truth.json` sits beside it mapping `tx_hash` to
service.

Nesting both under each hash would force a human labeler to answer both questions or
neither. Two files degrade gracefully: someone labeling real transactions can supply payer
truth alone and still get payer scoring, with the service axis reported unscored. The
labeling burden is what stands between this project and the real-data milestone, so the
extra burden is opt-in.

Both files are independently optional, and absence is normal rather than an error — the
pattern `ground_truth.json` and `hazards.json` already follow.

**One sentinel, not two.** `__ungroupable__` already means "belongs to no group", which
reads correctly on both axes: a payment with a generic or absent memo has no meaningful
service, exactly as a one-off payer has no meaningful group. Reusing it keeps a labeler's
vocabulary to a single special string.

## Scoring

`score()` does not change. It takes plain `predicted` / `truth` / `tiers` / `rules` dicts and
knows nothing about what the groups mean — it is axis-agnostic by construction. v0.1b calls
it once per axis.

That is the B-cubed rewrite paying off: the metric asks "did things that belong together end
up together", which is the same question on either axis.

`run_evaluate` returns both results, with the service result `None` when service truth is
absent. `render_evaluation` grows a second section.

The simulator gains service ground truth for every transaction it generates. Its existing
memo-drift hazard becomes a *service*-axis hazard: one payer whose memo drifts
`report-api` → `report-api-v2` → `reports` is one service under three names, so exact-string
matching will fragment it and score poorly on service recall. That is the measurement doing
its job.

## Reporting

Two breakdowns:

- **"Who paid you"** — payer axis, with the confident / needs-review split unchanged
- **"What they paid for"** — service axis, described as grouped by memo, no confidence claim

Each axis keeps its own explicit "not identified" line. A payment with no recognizable payer
and a payment with no meaningful memo are different gaps, and a reader should see both.

The CSV gains payer and service columns in place of the single `category_label` /
`confidence_tier` / `rule_matched` triple.

### A stronger money invariant

Both axes partition the same money, so the payer breakdown and the service breakdown must
**each independently sum to the same net total**. This is a stricter check than v0.1a had,
and it catches a class of bug the old one could not: if a transaction is dropped from one
axis or double-counted in the other, the two breakdowns stop agreeing.

## Testing

**The regression guard for the actual bug:** a per-rule calibration test built from the exact
dilution scenario — one confident rule at 100% precision over many transactions, another at
70% over few, aggregate landing above 0.95. Under the old aggregate gate that passes
silently; that *is* the defect. Under the per-rule floor the warning fires. The test carries
a comment explaining why the aggregate was insufficient, because someone will later wonder.

**Also required:**

- A payment with both a recognized sender and a specific memo receives **both** labels — the
  `elif` collapse this release exists to undo
- `memo_match` appears nowhere in the payer axis
- Money reconciles across ingest, net, payer lines, service lines, and CSV
- A missing `service_truth.json` leaves the payer axis fully scored — the real-data path
- A stale database is refused with an actionable message
- Service-axis accuracy is reported and carries no confidence claim

Every existing test that changes must carry recorded justification. A threshold quietly
loosened to make a failure disappear is the one thing this project does not do.

## Definition of done

- [ ] Cascade runs two independent passes; a transaction can carry both a payer and a service label
- [ ] `categorizations` is keyed on `(transaction_id, axis)`; stale databases refused
- [ ] `memo_match` no longer contributes to payer identification or the confident payer total
- [ ] Service axis reports descriptively with no confidence claim, and is scored against `service_truth.json`
- [ ] Calibration applies per confident rule at 0.95, not in aggregate
- [ ] Report shows both breakdowns, each with its own "not identified" line
- [ ] Both breakdowns independently reconcile to the same net
- [ ] A missing `service_truth.json` degrades cleanly to payer-only scoring
- [ ] The `time_cluster` sample size and verdict after the split are recorded, whatever they are
- [ ] README documents both ground-truth files and states that service groupings claim no confidence
- [ ] Full suite passes; every changed existing test has recorded justification

## Deliverable

Measured per-rule accuracy on both axes, the per-rule calibration outcome, and the
`time_cluster` verdict or its INSUFFICIENT DATA status after the split — the input to
deciding whether the service axis has earned a confidence claim, and whether `time_cluster`
survives.
