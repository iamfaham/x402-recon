# x402-recon v0.4 — Design

**Date:** 2026-08-27
**Status:** Approved for implementation planning
**Predecessors:** `2026-08-26-x402-recon-v0.3-design.md` and the four releases before it

## Purpose

v0.3 was validated against real payments on Base mainnet. That run also showed
what breaks next: the public RPC endpoint returned `503 no backend is currently
healthy` three times consecutively, and a single 30-day report cost roughly
5,000 sequential block-timestamp lookups.

v0.4 makes the tool survive the network it actually talks to, and makes the
repository something a stranger can install and contribute to.

This tool still only reads and summarizes payments a business has already
received. It never holds or moves funds, and it does not provide tax or
accounting advice.

## Scope

Four items:

1. **RPC resilience** — retry transient failures with backoff, without
   confusing them for block-range complaints.
2. **Batched block timestamps** — replace ~5,000 sequential calls with ~50
   batched ones, exactly rather than by estimation.
3. **A first-run-friendly command surface** — hide research tooling from the
   default help without breaking it.
4. **Open-source setup** — CI across three Pythons and three operating
   systems, a 3.11 floor, contributor and security policy, and packaging
   prepared for publication.

**Out of scope:** publishing to PyPI (requires a credential the implementer
does not hold — prepared but not executed), seller-side capture, and every
remaining Minor from v0.3's final review.

## 1. RPC resilience

### The decision that matters is three-way, not two-way

`get_logs` currently makes a binary choice on error: narrow the block span, or
give up. Real endpoints produce a third category, and v0.3 already shipped one
bug from conflating them — narrowing the span in response to a rate limit makes
rate limiting worse, because a narrower span means more requests.

The classification becomes:

| Condition | Response |
|---|---|
| The endpoint objects to the block range | **Narrow** the span and retry immediately (existing behavior) |
| HTTP 429, 502, 503, 504, a timeout, or a dropped connection | **Wait and retry** at the same span |
| Anything else | **Fail** immediately with the endpoint's own message |

A transient failure must never narrow the span, and a range complaint must
never sleep. Each is a distinct fix for a distinct problem, and applying the
wrong one makes the situation worse rather than merely failing to help.

### Backoff

Exponential with jitter: roughly 0.5s, 1s, 2s, 4s, each multiplied by a random
factor between 0.5 and 1.5 so that concurrent runs do not synchronize. Capped
at `MAX_RETRY_ATTEMPTS` (4) per request, and the cumulative sleep across a
single request bounded by `MAX_RETRY_SECONDS` (30) so a dead endpoint fails in
seconds rather than hanging.

Jitter matters because retries without it converge into a thundering herd —
the same reason a rate-limited client that retries on a fixed schedule stays
rate-limited.

### Visibility

Nothing may retry silently. Each retry prints one line naming the attempt, the
wait, and the reason, so a slow run is explicable rather than mysterious. This
is the same guarantee as the reject list: the tool does not do things to your
data or your time without saying so.

## 2. Batched block timestamps

### The cost being removed

`fetch_transactions` resolves a timestamp for every distinct block containing a
log. For a Tavily-sized month that is on the order of 5,000 sequential HTTP
round trips, cached per block but not batched — and it dominates a real run's
wall-clock time by an order of magnitude over everything else.

### Why not interpolation

The tempting fix is to fetch timestamps at chunk boundaries and interpolate
between them. **This release rejects that**, for the reason `blocks.py` already
records: Base targets two-second blocks but drifts, and an interpolated
timestamp at a date boundary silently moves a payment into or out of a report.
The project chose exact binary search over estimation once already; choosing
estimation here would contradict that for a speed gain we can get exactly.

### JSON-RPC batching

The JSON-RPC specification permits an array of request objects in one HTTP
call, answered by an array of responses. Fetching 5,000 timestamps becomes
about 50 HTTP requests at a batch size of 100, with identical results — the
same values, exactly, in far fewer round trips.

### Endpoints that refuse batches

Not every provider supports batching. A client must therefore:

1. Attempt a batched call.
2. If the endpoint rejects the **batch shape** — an HTTP error, or a single
   non-array response where an array was expected — fall back to sequential
   calls **and remember that** for the remainder of the run.
3. If the endpoint accepts the batch but reports errors on individual entries,
   that is real data, not a batching failure. Surface it per entry.

Distinguishing "you may not send arrays" from "one of your requests was bad" is
the whole subtlety; conflating them would silently disable batching against a
working endpoint, or silently hide a genuine error against a broken one.

The existing per-block cache is unchanged and sits in front of this: a batch is
only ever assembled from blocks not already cached.

## 3. Command surface

### The problem

Eleven subcommands, several of which exist to validate the tool rather than to
use it. A stranger running `--help` cannot tell which two they need.

### The mechanism, and its one wrinkle

`argparse` has no hidden-subcommand feature. The mechanism is
`help=argparse.SUPPRESS`, which removes a subcommand from the help listing
while leaving it **fully functional**. Nothing breaks: existing scripts,
existing documentation, and anyone who cloned the repository this week all
continue to work exactly as before.

The cost is discoverability, and it must be paid explicitly rather than
ignored:

- `x402-recon --advanced` lists the hidden commands with their help text.
- The default help ends with one line pointing at it.

A command that exists but cannot be found is worse than one that is merely
verbose.

### The split

**Visible** — what someone reconciling their own payments needs:
`discover`, `report`, `customers`, `fetch`, `ingest`, `categorize`

**Hidden** — machinery for validating the tool's own accuracy:
`simulate`, `shape`, `label`, `evaluate`

The bare-address and `--url` overview paths are unaffected and remain the
first thing the help describes.

## 4. Open-source setup

### Python floor

Drops from **3.13 to 3.11**. Verified: no PEP 695 generics, no `match`
statements, no 3.12-or-later stdlib. The only version-sensitive import is
`from datetime import UTC` in `categorize.py` and `simulate.py`, which is
3.11+ — so 3.11 is a `pyproject.toml` change alone, and 3.10 would require
rewriting those two imports.

3.13 was released in October 2024 and excludes most current installations. The
change costs one line and roughly triples the addressable install base.

### Continuous integration

GitHub Actions on push and pull request, running the full suite across the
matrix **3.11, 3.12, 3.13 × Ubuntu, macOS, Windows**.

The operating-system axis is not padding. This project has only ever been run
on one Windows machine, a terminal-encoding bug has already bitten once, and
two of the fixes in v0.3 were specifically for Windows file-locking behaviour
that would never have appeared on Linux. The matrix is how that stops being
luck.

### Packaging

`pyproject.toml` gains the metadata a PyPI listing needs: description,
authors, licence, README content type, keywords, classifiers, and project
URLs. The package must build cleanly and install from the built artifact.

**Publishing is not performed.** It requires a PyPI token the implementer does
not hold. Everything up to `uv publish` is prepared and verified; running it is
a hand-off, recorded as such.

### Contributor and security policy

`CONTRIBUTING.md` covering the development loop actually used here — `uv sync`,
`uv run pytest`, the no-runtime-dependencies rule, and the expectation that
behavioural changes arrive with tests.

`SECURITY.md` stating how to report a vulnerability, and — specific to this
tool — that it reads public chain data, sends no telemetry, and stores a cache
of counterparty addresses locally under `~/.x402-recon/`.

## Global constraints

Unchanged from v0.3 except the Python floor:

- **Python ≥3.11** (was ≥3.13). **Runtime dependencies MUST remain empty —
  stdlib only.** pytest dev-only.
- **Money is ALWAYS integers in micro-USDC. Never a float.**
- Nothing forced into a bucket; nothing silently dropped — now explicitly
  including retries, which must announce themselves.
- No user-facing string may advise on tax or accounting treatment.
- **Network access confined to `rpc.py` and `discover.py`**, both with
  injectable transports.
- **Output may only call payments "x402" when the address came from
  `discover`.**
- No test touches the network; no mainnet address in any committed fixture.
- `src/x402_recon/ingest.py` must not be modified.

## Definition of done

- [ ] Transient failures (429, 502, 503, 504, timeout, dropped connection) are
      retried with exponential backoff and jitter
- [ ] A transient failure never narrows the block span; a range complaint never
      sleeps
- [ ] Retries are bounded by both attempt count and cumulative wall time
- [ ] Every retry prints one line naming attempt, wait, and reason
- [ ] Block timestamps are fetched in JSON-RPC batches
- [ ] Batched and sequential paths return identical results for identical input
- [ ] An endpoint refusing the batch shape falls back to sequential and
      remembers it for the run
- [ ] An error on an individual batch entry is surfaced, not mistaken for a
      batching failure
- [ ] The per-block cache still prevents refetching, in front of batching
- [ ] Research subcommands are hidden from default help and still work
      unchanged
- [ ] `--advanced` lists them; the default help points at it
- [ ] Python floor is 3.11 and the suite passes on it
- [ ] CI runs the suite on 3.11/3.12/3.13 across Linux, macOS and Windows
- [ ] The package builds and installs from the built artifact
- [ ] `CONTRIBUTING.md` and `SECURITY.md` exist and describe this project
      specifically
- [ ] Full suite passes; no test touches the network; no mainnet address
      committed
- [ ] Publishing to PyPI is prepared, documented, and handed off unperformed

## Deliverable

A tool that survives a flaky public endpoint, reports a month in seconds rather
than minutes, presents two commands rather than eleven to someone seeing it for
the first time, and can be installed and contributed to by someone who is not
its author.
