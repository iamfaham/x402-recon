# x402-recon v0.3 — Design

**Date:** 2026-08-26
**Status:** Approved for implementation planning
**Predecessors:** `2026-08-18-ledger-v0-design.md`, `2026-08-19-ledger-v0.1a-design.md`,
`2026-08-19-ledger-v0.1b-design.md`, `2026-08-20-ledger-v0.1c-design.md`,
`2026-08-21-ledger-v0.2-design.md`

## Purpose

v0.2 built a pipeline that can read real payments off Base. It has never been pointed at
one, and a user who tried would need to know their own block numbers.

v0.3 closes exactly three gaps from `docs/production-readiness.md`: a `discover` command
that finds a seller's receiving address from their endpoint, a single command that runs the
whole pipeline, and the first real end-to-end run against Base mainnet.

This tool still only reads and summarizes payments a business has already received. It never
holds or moves funds, and it does not provide tax or accounting advice.

## Scope

**In scope:** P0 #7 (`discover`), P0 #6 (one-command UX, which subsumes date-based fetch),
P0 #1 (first real run), a pure-Python keccak256, and the caching those require.

**Out of scope, deliberately:** P0 #4 (reorganizing the nine existing subcommands),
seller-side capture, and every P1–P4 item. The `--help` wall is a real problem and it is not
this release's problem.

## The naming problem this release must not create

`fetch` pulls **all native USDC transfers to an address**, not x402-specific ones. A tool
called `x402-recon` that silently reports non-x402 revenue as x402 revenue would be
dishonest, and Tavily and Exa are exactly the readers who would notice.

**Provenance decides the label.** An address obtained from `discover` *is* an x402 `payTo` —
the seller's own 402 response said so — and inbound USDC there is x402 by construction. An
address typed in by the user is unverified, and its output says "USDC payments received"
with that limitation stated. The header line always records which case applies.

**A sample verifies the claim rather than asserting it.** See "Sampling instead of
filtering" below.

## Where the network lives

The v0.2 invariant was *"`rpc.py` is the only module permitted to open a socket."*
`discover` breaks it — it makes an ordinary HTTP GET, not a JSON-RPC POST. Rather than
widening `rpc.py` to hold an unrelated protocol, the invariant is restated:

> **Network access is confined to `rpc.py` and `discover.py`. Both take an injectable
> transport, and no test may exercise the real one.**

This keeps the property that actually mattered: every other stage is offline, testable, and
replayable from disk. A structural test asserts that no other module imports `urllib`, so
the rule is enforced rather than remembered.

## `discover.py`

One job: given a URL, make one unpaid request, parse the 402 response, return the payment
requirements.

**The 402 body shape varies by protocol version.** v1 carries an `accepts` array; v2 carries
an `accepted` object. The parser tolerates both and **fails loudly rather than guessing**
when `payTo` cannot be found — a wrong address produces a beautiful, entirely fictional
report, which is worse than an error.

**Fields consumed:** `payTo` (the receiving address), `network` (CAIP-2, e.g.
`eip155:8453`), `asset` (token contract), and `amount` where present.

**Validation before returning.** `network` must be `eip155:8453` (Base mainnet) and `asset`
must be native USDC (`0x833589fcd6edb6e08f4c7c32d4f71b54bda02913`). Anything else — Solana,
Polygon, bridged USDbC — is refused with a message naming what was found, because the
fetcher cannot read it.

**Politeness.** One request per invocation, a descriptive User-Agent, and no retry storm. A
402 without payment is the protocol behaving as designed and costs the seller nothing, but
that is not a licence to hammer.

## keccak256, and why it earns its place

Ethereum topic hashes are keccak256, which the standard library does not provide.
`hashlib.sha3_256` is **not** it: Ethereum uses original Keccak padding (`0x01`), NIST SHA-3
uses `0x06`. Using the wrong one yields plausible-looking wrong hashes — this is the classic
trap and the tests exist to catch it.

Roughly 80 lines of stdlib Keccak-f[1600]. It earns inclusion three ways:

1. It derives `AuthorizationUsed(address,bytes32)`'s topic without a pasted constant.
2. **It verifies a constant we already trust.** `TRANSFER_TOPIC0` is pinned in `chain.py`
   from an independent source. If our keccak of `"Transfer(address,address,uint256)"`
   reproduces it exactly, the implementation is validated *and* the pinned constant stops
   being an article of faith. Each checks the other.
3. It powers the x402 verification sample below.

## Sampling instead of filtering

Filtering every payment to EIP-3009 settlements was investigated and rejected on cost.
`AuthorizationUsed` indexes the **authorizer** (the payer), not the receiver, so it cannot be
filtered by the address we care about. Pulling every `AuthorizationUsed` on Base USDC across
30 days means millions of logs — x402 alone runs ~111k/day on Base before other EIP-3009
use. Checking per-transaction means one receipt call per payment: 8,701 requests for a
Tavily-sized month. Neither belongs in a command that should feel instant.

Instead: **check a bounded sample and report what was found.**

> Sample up to `X402_SAMPLE_SIZE` (50) transactions' receipts, count how many carry an
> `AuthorizationUsed` log from the USDC contract, and state the result.

Rendered as: *"Sampled 50 of 8,701 payments: 50 were EIP-3009 settlements, consistent with
x402."* Bounded cost, and it converts an assertion into a measurement — which is the thing
that makes this project's output worth trusting.

Full filtering remains possible later on a narrow range. It is not the default and not in
this release.

## The one command

### Entry forms

```bash
x402-recon 0x209693Bc…                            # bare address, last 30 days
x402-recon --url https://x402.tavily.com/search   # discover the payTo first
x402-recon 0x209693Bc… --from 2026-07-01 --to 2026-07-31
```

The default window is **30 days**, chosen to match the x402 Bazaar's own reporting window,
since that is what any external comparison will be against.

**Argument parsing, stated explicitly.** `cli.py` currently declares
`add_subparsers(dest="command", required=True)`, so a bare positional cannot reach the
parser. The resolution: the subparser becomes **not required**, and when the first argument
is not a recognised subcommand name it is treated as an address. `--url` with no positional
is equally valid. If neither an address nor a `--url` is given and no subcommand is named,
print help and exit non-zero. An address that fails a basic shape check (`0x` + 40 hex
characters) is rejected by name rather than being fetched as nonsense.

### Flow

Resolve address (via `discover` when `--url`) → resolve dates to blocks → consult cache and
fetch only missing ranges → ingest → categorize → render.

The four existing commands (`fetch`, `ingest`, `categorize`, `report`/`customers`) are
**unchanged** and remain available as escape hatches. This is a thin orchestrator over them,
not a rewrite: purely additive, so the existing 281 tests keep their meaning.

### Date to block: exact, not estimated

Resolution is **binary search over `eth_getBlockByNumber`**, not a block-time estimate. Base
targets 2-second blocks but drifts, and at a financial boundary an estimate silently includes
or drops real payments. Binary search costs ~20 requests and is exact.

Defined precisely: `--from D` resolves to the **first block whose timestamp is ≥
`D`T00:00:00Z**; `--to D` resolves to the **last block whose timestamp is ≤ `D`T23:59:59Z**.

### Cache

`~/.x402-recon/<address>.db` — SQLite, the existing schema plus a `fetched_ranges` table
recording which block ranges have been retrieved, so gaps are computable and re-runs fetch
only what is missing.

Adding that table is a **schema change**, and this project refuses rather than migrates. An
older cache database is reported and deleted rather than migrated — acceptable precisely
because it is a cache, and it must say so rather than failing cryptically.

`--no-cache` uses a temporary database and deletes it, for anyone who does not want
counterparty addresses persisted. The cache location is documented in `--help`.

### Adaptive chunking

A 30-day window is ~1.3M blocks. At v0.2's fixed 10,000-block span that is 130 round trips
to a public endpoint, which invites rate-limiting.

The client starts at a wide span, **halves on a "range too large" rejection, and remembers
what the endpoint accepted** for subsequent chunks. Combined with the cache, first runs are
tolerable and re-runs are instant.

## What it prints

```
x402-recon · 0x209693Bc…12287C
Base mainnet · 1–31 Jul 2026 · payTo discovered from x402.tavily.com

  Net received          $437.36    from 8,701 payments
  Distinct payers           249    34.9 payments each

Who actually came back
----------------------
                     payers    payments      revenue    share
  Returning (3+)        162       8,614      $433.33    98.9%
  Tried twice             0           0        $0.00     0.0%
  One-shot               87          87        $4.89     1.1%

Notes
-----
  · Payer grouping is uncalibrated on this data — no ground truth was
    supplied, so the split is shown but its accuracy is unmeasured.
  · Sampled 50 payments: 50 were EIP-3009 settlements, consistent with x402.
  · The chain records no memo, so what was bought cannot be shown — that
    lives in your request log, not on-chain.
  · Organizes payments you have already received. Not tax or accounting advice.
```

**Design decisions embedded above:**

- The header records **provenance** — discovered from a 402, or a raw address — because that
  is what licenses the word "x402" at all.
- On chain data the service axis is *always* empty, so a full "what they paid for" section
  would be noise on every run. It is demoted to a note.
- Every honesty guarantee from v0.2 survives, in the notes rather than interrupting the body.
- **When the probe-traffic ratio fires, its warning goes directly beneath the table**, not in
  the notes. For a service like OneSource that finding is the headline, not a caveat.

## Errors a first-time user will actually hit

Each must state what happened and what to do, never a traceback:

- The URL returns 200, not 402 — the endpoint may not be x402-paywalled.
- The 402 has no `payTo`, or an unrecognised body shape.
- The endpoint is on another network or another token.
- The address has no transactions in the window.
- The RPC endpoint rate-limits or refuses; suggest `--rpc-url`.
- An older cache database exists.
- The date range is inverted or in the future.

## Testing

### Automated — offline, always

- **keccak known-answer vectors**, including that
  `keccak256("Transfer(address,address,uint256)")` reproduces the pinned `TRANSFER_TOPIC0`,
  and an explicit test that the result differs from `hashlib.sha3_256` (the padding trap).
- **`discover` against recorded 402 bodies:** v1 `accepts` array, v2 `accepted` object,
  missing `payTo`, wrong network, wrong asset, a non-402 response, malformed JSON. Each
  failure names what it found.
- **Date→block binary search** against a fake chain, including a target falling between two
  blocks and a target outside the chain's range.
- **Adaptive chunking** against a transport that rejects wide ranges — asserts it narrows and
  completes rather than dying.
- **Cache gap computation** — pure logic; the part most likely to silently double-count or
  drop a range.
- **Combined overview rendering** in every state: probe-flagged and not, empty range,
  discovered vs raw address provenance.
- **Structural invariant:** no module other than `rpc.py` and `discover.py` imports `urllib`.

No test touches the network. No mainnet address appears in any committed fixture.

### Manual — the first real run, with an external oracle

This cannot be automated here (network egress is blocked in the implementation environment;
Base RPC returns HTTP 403). It is executed by the user and reported back.

It is not "run it and see if it looks fine." The Bazaar independently publishes Tavily's
figures — **8,701 calls from 249 unique payers over 30 days** — which is an external source
to check the whole pipeline against.

**Pre-registered before the run, so the result cannot be rationalised afterwards:**

> Fetching Tavily's discovered `payTo` over a comparable 30-day window should yield payment
> and distinct-payer counts **within 2× of 8,701 and 249**.

Deliberately not an exact match: the Bazaar counts API *calls* while this counts *on-chain
payments*, the windows will not align to the same hours, and free-tier or batched calls may
not settle one-to-one. Within 2× validates the plumbing. Exact agreement would be suspicious.

**Steps:**

1. `x402-recon --url https://x402.tavily.com/search --last 30d`
2. Record: the discovered `payTo`, payment count, distinct payers, wall-clock time, any
   rate-limiting, and the full rendered report.
3. Repeat for `https://api.exa.ai/search` and one OneSource endpoint.
4. For OneSource, confirm the **probe-traffic warning fires** — its published ratio is ~1.0,
   so if the warning does not appear, the detection is broken.

**Outcomes:**

- **Within 2×** — the pipeline is validated end-to-end against an independent source, and
  the outreach reports are in hand.
- **Outside 2×** — that is the finding. Fix before anything else; the divergence itself
  indicates where.
- **Fails to complete** — capture the error; resilience is under-built and that is the next
  work.

Expect the first run to surface something. Every prior release found defects only when the
data changed shape, and this is the first contact with data we did not generate.

## Global constraints

Unchanged from v0.2:

- Python ≥3.13. **Runtime dependencies MUST remain empty — stdlib only.** pytest dev-only.
- **Money is ALWAYS integers in micro-USDC. Never a float.** A refund is a positive amount
  with `tx_type='refund'`.
- Timestamps ISO 8601 UTC, `YYYY-MM-DDTHH:MM:SSZ`, zero-padded, TEXT.
- Nothing forced into a bucket; nothing silently dropped.
- No user-facing string may advise on tax or accounting treatment.
- `CALIBRATION_THRESHOLD = 0.95` and `MIN_VERDICT_SAMPLE = 20` unchanged.
- **Confidence is per-axis.** Service money never joins the payer axis's confident total.
- No test touches the network; no mainnet address in any committed fixture.

New to this release:

- **Network access confined to `rpc.py` and `discover.py`**, both with injectable transports.
- **The output may only call payments "x402" when the address came from `discover`.**

## Definition of done

- [ ] keccak256 implemented, verified against known vectors and against `TRANSFER_TOPIC0`
- [ ] A test proves the implementation differs from `hashlib.sha3_256`
- [ ] `discover` resolves `payTo` from both v1 and v2 402 body shapes
- [ ] `discover` refuses non-Base and non-native-USDC endpoints, naming what it found
- [ ] `discover` fails loudly when `payTo` is absent rather than guessing
- [ ] Dates resolve to blocks by exact binary search, boundaries defined as above
- [ ] Chunking adapts to what the endpoint accepts
- [ ] Cache under `~/.x402-recon/`, gaps computed, `--no-cache` available, old schema refused
      with a clear message
- [ ] A single command runs the whole pipeline from an address or a URL
- [ ] Combined overview renders as specified, with provenance in the header
- [ ] Probe-traffic warning renders beneath the table, not in the notes
- [ ] x402 sample check runs and reports what it found
- [ ] Output never claims "x402" for a raw, undiscovered address
- [ ] Every listed first-run error states what happened and what to do
- [ ] Structural test: only `rpc.py` and `discover.py` import `urllib`
- [ ] Full suite passes; no test touches the network; no mainnet address committed
- [ ] Manual run executed by the user and its result recorded against the 2× criterion

## Deliverable

A single command that takes a URL or an address and returns a seller's real customer
breakdown — validated end-to-end against an independently published figure, and honest about
which of its claims it has actually earned.
