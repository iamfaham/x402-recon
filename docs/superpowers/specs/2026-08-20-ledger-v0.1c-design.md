# Ledger v0.1c — Design

**Date:** 2026-08-20
**Status:** Approved for implementation planning
**Predecessors:** `2026-08-18-ledger-v0-design.md`, `2026-08-19-ledger-v0.1a-design.md`, `2026-08-19-ledger-v0.1b-design.md`

## Purpose

Two questions have been deferred across previous releases. v0.1c makes both answerable and
then **answers them**.

This tool still only reads and summarizes transactions a business has already received. It
never holds or moves funds, and it does not provide tax or accounting advice.

## Why this release decides rather than measures

`time_cluster` is entering its third release undecided. v0.1a could not measure it — the
dataset made it structurally impossible for the rule to be right. v0.1b measured it honestly
and withheld on sample size. If v0.1c measures and defers again, the pre-registered 0.70
threshold stops being a commitment and becomes theatre — the exact self-deception the whole
measurement apparatus exists to prevent.

The service axis is in the same position. v0.1b named its precision as the input to a
confidence decision, and that decision is still pending.

So both criteria bind this release. Once the evidence exists, the thresholds decide.

## The two open questions

### 1. Service precision is unfalsifiable

`simulate.py` derives `service_truth` from the memo for essentially every generator. The only
divergence is the memo-drift hazard — one service under three memo names — which fragments
and therefore costs **recall**, never precision.

No hazard exists of the inverse shape: **one memo string covering two genuinely different
services**. Merging is the only thing B-cubed precision penalizes, so that asymmetry is why
the published 100.0% cannot fail by construction.

### 2. `time_cluster` has never had enough evidence

At seed 42 it fires 13 times, measuring 87.7% B-cubed precision — above its 0.70 threshold —
but 13 is below `MIN_VERDICT_SAMPLE = 20`, so the verdict correctly renders INSUFFICIENT
DATA.

v0.1b fixed a latent bug in which `generate_batch`'s `count` parameter was shadowed by a loop
variable, making `--count` a no-op. It now works, so raising it is the honest lever for
reaching 20 firings — more traffic under the same generation rules, with no cascade tuning.

## Pre-registered criteria

Both are fixed **before** measurement, so neither result can be rationalized afterwards.

> **`time_cluster` survives** only if it achieves **B³ precision ≥ 0.70** on transactions it
> assigned, with at least `MIN_VERDICT_SAMPLE` (20) firings. Unchanged from v0.1a.

> **The service axis earns a confidence claim** only if `memo_match` achieves **B³ precision
> ≥ `CALIBRATION_THRESHOLD` (0.95)** with at least `MIN_VERDICT_SAMPLE` (20) firings.

The service criterion deliberately invents no new number. It reuses the floor every confident
rule is already held to, which makes it self-consistent: a rule that could not survive the
gate it would then be subject to has no business claiming confidence in the first place.

Precision alone decides, on both axes. The floor exists to prevent false confidence, not to
mandate coverage — a rule that fires rarely but is right when it does is trustworthy, just
narrow. Recall is reported but does not gate.

## The inverse memo hazard

`HAZARD_SHARED_MEMO_DIFFERENT_SERVICES`: two recurring agents both send the memo
`"monthly-plan"` while buying genuinely different things. One's true service is
`weather-api`, the other's is `llm-inference`. `memo_match` groups them into a single
`service:monthly-plan`; service truth says they belong apart. Service precision can fall for
the first time.

### Its senders repeat, deliberately

This is the design decision that makes the staged measurement clean. A hazard built from
one-off senders would land in `time_cluster` or `none` on the payer axis and perturb the very
rule this release is deciding — the staged measurement would then show `time_cluster` moving
with no way to attribute it. Repeating senders mean `sender_match` claims these transactions
confidently, so **the hazard is payer-axis-neutral by construction** and its effect is
isolated to the service axis.

### Sizing

Large enough to move precision measurably, small enough that hazard-affected transactions
remain a minority of the dataset — the existing `HazardConfig` invariant. A count in the same
range as the other hazards (roughly 6–10) is expected to put service precision near 90%.

Landing near the threshold is preferable to landing comfortably past it. A criterion that
only ever confirms what was already believed is not doing any work.

## What each branch does

Both criteria may go either way, so both branches are specified. A plan describing only the
expected outcome is not a commitment.

### `time_cluster`

**Passes** — the rule stays and the verdict is recorded as settled rather than pending.
`MIN_VERDICT_SAMPLE` remains in place; it did its job.

**Fails** — the rule is removed. The payer cascade becomes `sender_match` → `none`. v0.1a
already de-risked this branch: it feared that removing `time_cluster` would empty the
uncertain tier and leave calibration vacuous, and resolved that by redefining calibration
absolutely rather than as a contrast between tiers. `UNCERTAIN` also survives regardless,
since uncategorized payer rows carry it.

### The service axis

**Fails** — service rows stay `DESCRIPTIVE`. The README records the measured figure and why
it fell short.

**Passes** — service rows become `CONFIDENT`. The "claim no confidence" prose goes,
`render_axis_results` passes `claims_confidence=True` for the service axis, and `memo_match`
becomes subject to the per-rule calibration floor like any other confident rule.

In that branch the service axis mirrors the payer axis's tiering: rows `memo_match` claimed
become `CONFIDENT`, and rows it declined become `UNCERTAIN` alongside their `uncategorized`
label — the same shape the payer axis already uses. `DESCRIPTIVE` then has no remaining user
and is removed rather than left as a tier nothing carries.

If the criterion fails, `DESCRIPTIVE` stays exactly as it is and remains correct: the axis is
still stating rather than claiming.

### The trap in the passing branch

**Service money must not join the payer axis's "Confidently identified" total.**

That total answers *we know who paid you*. Folding a service figure into it would recreate
precisely the defect v0.1b existed to remove: two different claims summed into one number a
reader interprets as identity.

Confidence is per-axis. Each axis may earn its own, and they stay separate in the report.
Everything else in that branch is mechanical; this is the one change that would look like a
natural consequence of promotion while quietly undoing the previous release.

## Measurement

### Three stages, in order

1. **Baseline** at `count=120` on today's dataset. Should reproduce v0.1b's published figures
   exactly, confirming nothing drifted underneath the release.
2. **Plus the hazard**, still at `count=120`. Isolates the hazard's effect on service
   precision.
3. **Plus a raised count**, until `time_cluster` clears 20 firings. Isolates the count's
   effect.

All three are recorded. The third becomes canonical, and both criteria are applied to it.

Staging matters because both levers move the numbers. Pulling them together and watching a
figure shift would leave no way to say which caused it — and binding decisions are about to
rest on those figures.

### The canonical count

Not knowable in advance: it depends on how dense traffic must become before one-off payments
start landing within five minutes of each other. Clustering rises faster than linearly with
density, since it depends on pairs falling inside the window rather than on volume alone.

**Start at `count=300`** — roughly double the current 145 transactions, which should more than
double the 13 firings if the relationship is even mildly superlinear. Measure; if it falls
short of 20, raise and measure again. Record whichever N was used and how many firings it
produced.

That N is documented in the README, because v0.1a and v0.1b both used 120 and future releases
need to compare like with like.

### One check that comes free

Raising the count adds untagged filler, so the hazard *fraction* falls and the minority
invariant holds more easily rather than less. Worth confirming rather than assuming, since
the test pinning it currently runs at 120.

## Both verdicts are computed, not narrated

`time_cluster` already prints `PASSES`/`FAILS` against its constant. The service decision gets
the same treatment: a `service_confidence_verdict()` alongside `time_cluster_verdict()`,
printing the measured precision against 0.95 and its outcome, and withholding below
`MIN_VERDICT_SAMPLE` exactly as the existing verdict does.

A decision this release exists to make should not arrive as prose a human wrote after looking
at a number.

## Cleanup riding along

One deferred finding, because it sits on the axis being decided:
`_render_evaluation_body` prints *"of the payments from one payer, how many were found"*
verbatim on the service axis, where it should read *one service*. Small, but it is a recall
figure mislabelled as answering a payer question, inside the section whose entire purpose is
that it does not.

The other deferred minors in git history stay deferred — cosmetic and unrelated to this work.

## Testing

- The hazard is generated: same memo, at least two distinct true services
- The hazard is payer-axis-neutral: its senders repeat, so `sender_match` claims them and
  `time_cluster`'s firing count is unaffected by its presence
- `service_confidence_verdict` returns PASSES at or above 0.95, FAILS below, and withholds
  below `MIN_VERDICT_SAMPLE` — one constructed case each
- The hazard-minority invariant holds at the canonical count, not only at 120
- Whichever branch each decision takes, its consequences are covered: if `time_cluster` is
  removed, that no payer row carries `RULE_TIME_CLUSTER` and the report still renders; if the
  service axis is promoted, that its money remains outside the payer confident total

Every changed existing test carries recorded justification. A threshold quietly loosened to
make a failure disappear is the one thing this project does not do.

## Definition of done

- [ ] `HAZARD_SHARED_MEMO_DIFFERENT_SERVICES` generated, payer-axis-neutral, with correct
      service truth
- [ ] Service precision is falsifiable — it is no longer 100.0% by construction
- [ ] Three staged measurements recorded, each change's effect attributable
- [ ] A canonical count is chosen, documented, and `time_cluster` clears 20 firings on it
- [ ] `service_confidence_verdict()` exists and prints a computed verdict
- [ ] **The `time_cluster` criterion is applied and acted on** — kept or removed, not deferred
- [ ] **The service confidence criterion is applied and acted on** — promoted or not, not deferred
- [ ] If promoted, service money stays out of the payer axis's confident total
- [ ] The service axis's recall description says *service*, not *payer*
- [ ] README and `docs/sample-report.md` record the canonical count, both verdicts, and the
      v0.1b caveat's resolution
- [ ] Full suite passes; every changed existing test has recorded justification

## Deliverable

Two settled decisions with their evidence: whether `time_cluster` survives its
pre-registered threshold on adequate evidence, and whether the service axis has earned a
confidence claim on a dataset where its precision could actually have failed.
