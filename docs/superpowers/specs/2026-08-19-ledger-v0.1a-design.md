# Ledger v0.1a — Design

**Date:** 2026-08-19
**Status:** Approved for implementation planning
**Predecessor:** `docs/superpowers/specs/2026-08-18-ledger-v0-design.md`

## Purpose

v0 shipped a working pipeline whose headline accuracy numbers cannot be trusted. The
simulated dataset structurally cannot catch either confident rule being wrong, and the
scorer rewards one class of error while punishing another. v0.1a rebuilds the measurement
apparatus so the numbers mean what they claim, then stops — the decision about the
`time_cluster` rule is deliberately deferred to v0.1b, after measurement.

This tool still only reads and summarizes transactions a business has already received. It
never holds or moves funds, and it does not provide tax or accounting advice.

## Why measurement first

Three facts from v0's final review:

1. `time_cluster` scored 0% accuracy — but that is an artifact, not a measurement. One-off
   senders are appended last under a monotonic clock, so every cluster the rule forms is
   composed purely of ungroupable transactions, and grouping an ungroupable transaction is
   wrong by definition. The rule is guaranteed 0% regardless of its merit.
2. The confident rules scored 100% — but no unrelated one-off payers share a specific memo,
   and `sender_match` intercepts the only cross-group memo before `memo_match` sees it. The
   dataset cannot falsify either rule.
3. The scorer's majority-vote scheme penalizes merging two payers but rewards splitting one
   payer across several groups. It is asymmetric in our favour.

Deciding the fate of `time_cluster` on this evidence would be exactly the self-deception the
product exists to prevent.

## Scope

**In scope for v0.1a:**
- Refunds represented as a typed field, with net reporting
- A simulator that generates genuinely adversarial data on one shared timeline
- B-cubed scoring, replacing majority-vote purity
- Per-rule metric reporting
- Behavior-affecting cleanup from the v0 deferred-minor backlog

**Explicitly deferred to v0.1b (after measurement):**
- Acting on the `time_cluster` result — removing the rule, or committing to keep it
- Any replacement rule, and the consequences for the calibration metric

The division is precise: **v0.1a measures and recommends; v0.1b decides and acts.** v0.1a
ends by applying the pre-registered criterion to a real number and recording what it implies.
No rule is added or removed in v0.1a.

**Still out of scope (unchanged from v0):**
- Real transaction data (Base Sepolia or a public x402 dataset)
- Report readability work — payer aliases, human cluster names, distinguishing "no theory"
  from "weak theory". Deferred pending customer validation signal.
- PDF output, a second payment rail, accounting-software integration, tax advice

## The pre-registered decision criterion

Recorded here **before** measurement, so the result cannot be rationalized after the fact:

> `time_cluster` survives into v0.1b only if it achieves **B³ precision ≥ 0.70** on
> transactions it assigned, measured on the v0.1a adversarial dataset.

B³ precision is the right question for this rule because it asks "when the rule grouped
payments together, did they belong together" — the false-confidence question. Recall is not
this rule's responsibility; it only ever fires as a fallback after the confident rules decline.

The bar is high rather than lenient because a wrong cluster asserts that several unrelated
payments came from one payer. Even flagged uncertain, that plants a false idea. An
`uncategorized` transaction says "I don't know", which is honest and costs the reader
nothing.

## Known consequence to carry into v0.1b

If `time_cluster` is removed, the calibration metric goes vacuous. The uncertain tier is
populated only by transactions that were grouped, `uncategorized` transactions are excluded
from the grouped set by construction, and `time_cluster` is the sole rule producing
grouped-but-uncertain rows. Remove it and `uncertain_count` falls to zero, leaving the
confident-vs-uncertain contrast with nothing to contrast against.

A cascade of only confident rules can still be correct, but it can no longer demonstrate
that its confidence means anything. v0.1b must therefore answer two questions, not one:
is the rule good enough to keep, and if not, what takes its place?

## Refunds

### Schema

`transactions` gains one column:

| Column | Type | Notes |
|---|---|---|
| `tx_type` | TEXT NOT NULL DEFAULT `'payment'` | `payment` or `refund` |

Amounts remain non-negative integers in micro-USDC. A refund is a **positive** amount with
`tx_type='refund'`, which preserves the existing "reject negative amounts" validation that
catches malformed data.

### Ingest

`tx_type` is optional in source JSON and defaults to `payment` when absent, so existing
`transactions.json` files and real data sources with no refund concept keep working. Any
value other than `payment` or `refund` is a reject with a clear reason, like any other
invalid field.

### Schema versioning

`init_schema` uses `CREATE TABLE IF NOT EXISTS`, so an existing database would silently miss
the new column and fail later with a raw sqlite error. A `schema_version` table makes a
stale database fail immediately with an actionable message: the schema is out of date, delete
the database and re-ingest. Migration is deliberately not supported — `*.db` is gitignored
scratch that regenerates in seconds, and refusing clearly beats migrating badly.

The version check runs in `init_schema`, which every database-touching command already calls
before doing work. A stale database therefore fails on `ingest`, `categorize`, `report`, and
`evaluate` alike, rather than only on the command that happens to touch the new column.

### Reporting

The summary gains a gross / refunded / net structure rather than a single total. Each
category line nets its own refunds, so a payer who refunded half their spend shows their
true contribution. **The headline total a business owner reads becomes net**, since that is
the figure that represents revenue.

`format_usdc` currently renders negatives as `$-1.50`, because it splits on the decimal point
after formatting. Net figures can legitimately go negative in a range where refunds exceed
payments, so this becomes `-$1.50`.

### Categorize and evaluate

No logic change. A refund from a known sender groups with that sender like any other
transaction, and ground truth treats it identically.

## Simulator

### The structural change

Today one monotonic clock advances while each phase appends in sequence, which is precisely
why one-off senders form a segregated tail. That model is replaced: each actor generates its
activity independently across a shared time window, then all events merge and sort by
timestamp. Interleaving stops being a feature to add and becomes a property of how generation
works.

Determinism is preserved — same seed, same output — with ties broken on `tx_hash` so equal
timestamps cannot reorder between runs.

### Hazards

| Hazard | Rule it attacks | Ground truth |
|---|---|---|
| One-offs interleaved into agent bursts | `time_cluster` — supplies both plausible-but-wrong and plausible-and-right cases | ungroupable |
| Two unrelated payers sharing a specific memo | `memo_match` — it will collapse them | different groups |
| Mid-burst address rotation | `sender_match` — it will split one payer in two | one group |
| Memo drift over an agent's life | `memo_match` — the grouping key changes underneath it | one group |
| Wide amount variance, sub-cent to large | none directly; stresses money formatting and totals | unchanged |
| Refunds following payments | none directly; stresses net reporting | same group as the payment |
| Out-of-order arrival | none directly; proves no stage assumes input order | unchanged |

Mid-burst rotation interlocks with the scorer work: it manufactures genuine fragmentation,
which is exactly what B-cubed is being adopted to detect. Without this hazard the scorer
change would have nothing to catch.

### Keeping the dataset interpretable

A dataset where everything is adversarial is as uninformative as one where nothing is: if
every rule fails on every case, the metrics cannot indicate which weakness matters.

Concretely: **hazard-affected transactions must remain a minority of the dataset**, and every
rule must retain a clear population of ordinary cases it is expected to get right. Each
hazard's frequency is a named, configurable parameter with a stated default, so the dataset's
difficulty is a deliberate setting rather than an accident of generation — and so a future
change in the metrics can be attributed to a rule change rather than a silent drift in
dataset difficulty.

## Scoring: B-cubed

### Why the current scheme fails

Majority-vote purity maps each predicted group to its majority true group and counts matches.
Merging two payers is punished, because minority members score wrong. Splitting one payer
across three groups is rewarded, because each fragment's majority is still that payer. The
metric punishes one error and pays a bonus for the other.

### The replacement

For each transaction, let P be its predicted group and T its true group:

- **B³ precision** = |P ∩ T| / |P| — of the payments grouped *with* me, how many belong with me
- **B³ recall** = |P ∩ T| / |T| — of the payments that belong with me, how many got grouped with me

Both averaged across all transactions. Fragmentation craters recall; merging craters
precision. Neither error hides.

These map onto the product's own language: B³ precision is the false-confidence question,
B³ recall is the coverage question.

### Ungroupable transactions need no special case

Treat each genuinely-ungroupable transaction as its own true group of one, and each
`uncategorized` transaction as its own predicted group of one. Correct behavior then falls
out structurally:

| Situation | Result | Interpretation |
|---|---|---|
| Ungroupable, left uncategorized | precision 1.0, recall 1.0 | correctly declined to guess |
| Ungroupable, swept into a cluster of 7 | precision ≈0.14 | falsely grouped, heavily penalized |
| Real payer, left uncategorized | recall 1/9 | missed coverage, no false claim |
| One payer split across 3 clusters | precision 1.0, recall ≈0.33 | fragmentation, now visible |

The explicit `truth != UNGROUPABLE` guard added during v0 is removed. It existed to
compensate for the majority-vote scheme's blind spot; B-cubed handles the case structurally.

### Per-rule reporting

Metrics are broken out by `rule_matched` in addition to by tier, so each rule's contribution
is separately visible. This is what makes the pre-registered criterion measurable.

### Comparability

The new figures are **not comparable** to v0's precision 79.8% / recall 100%. The definition
changed; the movement is neither a regression nor an improvement. The README must state this
explicitly, or the next reader will draw a false conclusion from the difference.

## Cleanup

Behavior-affecting items only, carried from the v0 deferred-minor backlog.

### Vocabulary consolidation

`UNGROUPABLE` moves from `simulate.py` to `models.py`, where the canonical data shapes
already live. It is ground-truth vocabulary, not simulator vocabulary — a human labeling real
transactions needs it, and the simulator will not exist in that workflow.

This also removes the `evaluate.py → simulate.py` dependency flagged in v0's final review,
so the evaluation harness no longer imports from the simulator at all.

The same move consolidates the timestamp format — currently defined in `ingest.py`,
`categorize.py`, `simulate.py`, and implicitly in `report._bounds` — and the tier and rule
vocabulary, currently split between `categorize.py` and hardcoded SQL literals in
`report.py`. `models.py` depends on nothing internal, so no import cycle arises.

### Money contract

- `usdc_to_micro` raises `ValueError` on malformed input rather than leaking
  `decimal.InvalidOperation`, matching its documented contract.
- Its decimal-place gate normalizes before checking the exponent, so `"1.1000000"` is
  accepted rather than wrongly rejected — the value is exactly representable in micro-USDC.

Both are latent bugs today, reachable once real decimal-string data arrives.

### Error handling

A missing source directory, malformed `transactions.json`, malformed `ground_truth.json`, or
a stale database schema each produce a clean message and a non-zero exit code rather than a
traceback. The v0 principle is unchanged — fail loudly rather than quietly wrong — but a
stack trace is not a message a business owner can act on.

### Ground truth contract documentation

The `ground_truth.json` format and the `__ungroupable__` sentinel are documented in the
README. A human labeling real transactions currently has no way to learn either, which makes
it a prerequisite for the real-data milestone being usable at all.

## Testing

### The invariant that matters most

The money-reconciliation test extends to cover refunds: gross − refunds = net, and all four
quantities — ingested, summary total, sum of breakdown lines, and CSV column — still
reconcile exactly in integer micro-USDC. Refunds change this arithmetic, so the test must
grow with it.

### New coverage

- One test per simulator hazard, proving it is actually generated
- B-cubed scoring against hand-built cases where fragmentation, merging, and
  correctly-declined-ungroupable each produce a known score
- Per-rule metric breakdown reports each rule separately
- Refund netting; negative net renders as `-$1.50`; unknown `tx_type` rejected
- Stale schema produces its actionable message
- CLI error paths: missing source directory, malformed JSON
- `usdc_to_micro` raises `ValueError` on garbage and accepts `"1.1000000"`

### On the existing 87 tests

The simulator rewrite will legitimately invalidate some statistical assertions that encode
today's tail-structured dataset. Every such change must be a deliberate, justified correction
with its reasoning recorded — never a threshold quietly loosened to make a failure go away.
That distinction is the difference between updating a test and defeating it.

## Definition of done

- [ ] Refunds flow end to end: generated, ingested, categorized, netted in the report
- [ ] The simulator generates every hazard in the table above, each with correct ground truth
- [ ] Scoring is B-cubed, with the `UNGROUPABLE` special case removed
- [ ] Metrics are reported per rule as well as per tier
- [ ] `evaluate.py` no longer imports from `simulate.py`
- [ ] The measured B³ precision for `time_cluster` is recorded, and the pre-registered
      criterion applied to produce a keep/kill recommendation for v0.1b
- [ ] README states the new numbers are not comparable to v0's, and documents the
      `ground_truth.json` contract
- [ ] Full suite passes; every changed existing test has recorded justification

## Deliverable into v0.1b

A recorded measurement and a recommendation: whether `time_cluster` clears B³ precision ≥ 0.70,
and the per-rule figures for every rule. v0.1b designs what follows from that result, including
the calibration-metric question if the rule does not survive.
