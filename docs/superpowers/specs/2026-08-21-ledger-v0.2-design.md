# Ledger v0.2 — Design

**Date:** 2026-08-21
**Status:** Approved for implementation planning
**Predecessors:** `2026-08-18-ledger-v0-design.md`, `2026-08-19-ledger-v0.1a-design.md`,
`2026-08-19-ledger-v0.1b-design.md`, `2026-08-20-ledger-v0.1c-design.md`

## Purpose

Every claim this tool makes rests on simulated data. v0.2 puts it in front of real
money for the first time.

This tool still only reads and summarizes transactions a business has already
received. It never holds or moves funds, and it does not provide tax or accounting
advice.

## Why simulation has run out

v0.1c settled two questions against pre-registered thresholds, and in doing so
established the ceiling of what synthetic data can settle. Both verdicts depend on
generator parameters chosen by the same person who wrote the criteria: a hazard size
of 12 instead of 8 flips the service verdict, and a different seed flips
`time_cluster`. The measurements doc records this outright.

No further synthetic tuning resolves it. The dataset cannot surprise us, because we
wrote it.

## What the chain does and does not carry

x402 settles on-chain through EIP-3009 `transferWithAuthorization`, whose payload is
seven fields: `from`, `to`, `value`, `validAfter`, `validBefore`, `nonce`,
`signature`. None of them identify the resource purchased. That identity lives in the
HTTP layer — the `X-PAYMENT` header and the requested URL — which the seller and the
facilitator observe and the chain never records.

The consequence for this codebase is specific. `memo` is the only input to the service
axis. Chain data has no memo, so `memo_match` cannot fire, and the 96.2% precision
v0.1c measured is neither testable nor applicable here.

**So the payer axis meets reality in v0.2 and the service axis does not.** Seller-side
capture, which carries both, is v0.3.

## Scope

**In scope:** fetching real USDC payments received by one address on Base mainnet,
ingesting them through the unchanged pipeline, producing a report, hand-labeling a
sample, and settling one pre-registered question about whether `sender_match` earns
its confidence claim on real data.

**Out of scope:** any change to the categorization rules, the service axis,
seller-side capture, and the deferred minors carried from v0.1c.

## The claim boundary

The report currently prints *"Confidently identified (who paid you)"* on any dataset,
backed by precision measured entirely on simulation. After v0.2 three states exist and
the report must distinguish them:

| Data | Ground truth | What may be claimed |
|---|---|---|
| Simulated | Present | Confidence claim, calibrated, as today |
| Real, sample labeled | Partial | Calibrated **on the labeled portion**, with N stated |
| Real, unlabeled | Absent | Grouping only — claim marked uncalibrated for this dataset |

The third row is the default for anyone running Ledger on their own data, which is
every real user. It is the most important line in the release, not an edge case.

The state is **derived, never declared**: the report computes how much of the range it
is reporting on appears in `ground_truth`. There is no provenance flag for anyone to
set wrongly.

## Money survives contact with reality unchanged

USDC on Base has 6 decimals, so a raw transfer value **is** an integer count of
micro-USDC. No conversion, no rounding, no float anywhere on the ingest path. The
money invariant holds across the boundary without special handling.

Native USDC on Base is `0x833589fCD6eDb6E08f4c7C32D4f71b54bdA02913` (Circle's
FiatTokenProxy, 6 decimals). The older bridged **USDbC** at
`0xd9aAEc86B65D86f6A7B5B1b0c42FFA531710b6CA` is a different token; including it would
inflate totals. Only native USDC is fetched, and the exclusion is explicit.

## The `fetch` command

```
ledger fetch --receiver 0xABC... --network base --from 2026-07-01 --to 2026-07-31 --out sample/real
```

It writes the same JSON file shape `simulate` writes. `ingest` is untouched. **Network
access exists in this one command and nowhere else in the codebase**, so every
downstream stage stays offline and testable, and a fetched batch is replayable from
disk.

### Transport

JSON-RPC over `urllib.request` against the public Base RPC endpoint
`https://mainnet.base.org` — stdlib only, no API key, no new dependency. The endpoint
is overridable by flag so a user with their own node or provider is not forced through
a shared one. `eth_getLogs` filtered to the USDC contract and the
`Transfer(address,address,uint256)` topic, with the receiver address as the indexed
`to` parameter.

Public RPC endpoints cap block ranges per request. The fetcher walks the requested
range in chunks and resumes cleanly rather than failing the whole batch.

### Field mapping

Every value comes from the log or its block. Nothing is inferred.

| `Transaction` field | Source |
|---|---|
| `tx_hash` | `log.transactionHash` |
| `sender_address` | `Transfer` topic 1 (`from`) |
| `receiver_address` | `Transfer` topic 2 (`to`) |
| `amount_micro_usdc` | `int(log.data, 16)` — already micro-USDC |
| `timestamp` | block timestamp, formatted to `TIMESTAMP_FORMAT` |
| `memo` | `None` — the chain has none |
| `chain` | `"base"` |
| `raw_payload` | the raw log JSON, preserved verbatim |
| `tx_type` | see below |

### Refunds

The fetcher queries both directions. Transfers *to* the receiver are `payment`;
transfers *from* the receiver back to an address that previously paid it are `refund`,
stored as a **positive** amount with `tx_type='refund'` — the shape the model already
requires. Refunds have been simulated since v0; this is the first time they meet real
money.

### x402-only is a flag, not the default

`transferWithAuthorization` emits an `AuthorizationUsed` event alongside the
`Transfer`, so x402-settled payments are identifiable. This is available as
`--x402-only` for isolating agent traffic, but the default fetches all native USDC
received. Ledger reconciles *payments a business received*, and a business taking both
agent and ordinary payments wants both in the report.

### Failure handling

A malformed or unexpected log is skipped with a stated reason, in the same shape
`ingest` already uses for rejected rows, and the count is reported. **The fetcher never
silently drops a transfer** — the same guarantee as the rest of the pipeline.

## The staged measurement

Four stages, in **commit order**. Git is the audit trail: this spec — which fixes the
criterion — is committed before any real data is fetched, and the labels are committed
after. The criterion provably could not have been fitted to the result.

### Stage 1 — Shape, no scores

`ledger shape` reports only structural facts about the fetched batch:

- transaction count and date span
- distinct sender addresses
- the repeat distribution — how many senders appear once, twice, three-or-more, and
  what share of money each band carries
- how many transactions `sender_match` would claim at the configured
  `min_occurrences`
- refund count

**It never computes precision or recall.** Its job is to tell you whether the sample
bar is reachable and which branch you are heading for. It must not be able to reveal
the answer, because seeing the answer before labeling would let labeling drift toward
it.

### Stage 2 — Label, and the trap that must not be repeated

`ledger label` emits a worksheet of distinct senders with counts and volumes. **A human
fills it in. The tool never does.**

If "these transactions came from the same entity" is decided *by looking at the sender
address*, then `sender_match` scores 100% by construction and the measurement is
worthless. This is exactly the defect v0.1b shipped when service truth was derived from
the memo, and which v0.1c spent a release fixing. It would be the third occurrence of
one failure mode: **truth derived from the signal being tested.**

Therefore labeling evidence must be independent of the sender address — Basenames,
explorer entity labels, funding-graph common ancestry, published agent identities.

**Any transaction whose only evidence is the address itself is marked unlabelable, not
labeled.**

Partial truth is fine: `score()` already restricts itself to transactions present in
truth (`scored = [h for h in predicted if h in truth]`). Labeling coverage becomes a
reported number in its own right.

### Stage 3 — Confirm reachability, do not renegotiate

The criterion is fixed **here, in this spec**, before any real transaction has been
fetched:

> **`sender_match` earns its confidence claim on real data** only if it achieves **B³
> precision ≥ `CALIBRATION_THRESHOLD` (0.95)** on at least `MIN_VERDICT_SAMPLE` (20)
> independently-labeled transactions.

No new number is invented. It reuses the floor every confident rule is already held to
— the same self-consistency argument v0.1c used for the service axis.

**Shape cannot move this threshold.** Stage 1 exists to tell you which branch you are
heading for and whether the sample bar is reachable — not to tune the bar to what the
data happens to offer. If shape shows fewer than 20 independently-labelable
transactions, the correct response is the insufficient-data branch, never a lowered
`MIN_VERDICT_SAMPLE`. Discovering a bar is hard to clear is not evidence the bar is
wrong.

This is stricter than the v0.1c staging, and deliberately so. There, the canonical
count was genuinely unknowable in advance and shape had to inform it. Here nothing
about the data can justify moving a floor inherited from three prior releases.

### Stage 4 — Verdict, computed and acted on

The verdict prints against its constant, as both previous verdicts did. It is not
prose written after looking at a number.

## Three branches, all specified

**Earns.** The confidence claim stands on real data at the measured N. README and
sample report record the figure, the labeled sample size, and the coverage.

**Does not earn.** `sender_match` keeps grouping but the payer axis's confidence claim
is marked uncalibrated on real data pending a larger or better-labeled sample. The
synthetic calibration is not deleted — it remains true of synthetic data — but it stops
being presented as transferable.

**Insufficient data.** Fewer than 20 independently-labelable transactions exist.

This third branch differs from every previous "insufficient" in this project. On
synthetic data, INSUFFICIENT DATA was always fixable by raising `--count`, which is why
v0.1c ruled that deferring a third time would be theatre. On real data there may simply
not be 20 independently-labelable transactions, and **no lever exists to change that**.
Reporting the limit honestly is the correct outcome, not a deferral — and the release
records what would raise it (a larger date range, a busier receiver, or the seller-side
capture v0.3 brings).

## What the user sees

### The confidence claim, unlabeled

```
  Confidently identified (who paid you): $1,204.831
  Needs review (who paid you):           $  387.220

  ! No ground truth was supplied for this data, so "confidently" is
    uncalibrated here. The grouping is shown; its accuracy on this
    dataset is unmeasured.
```

### The confidence claim, partially labeled

```
  ! Accuracy measured on 24 of 312 payments (7.7% labeled):
    sender_match B-cubed precision 91.3%. The rest are grouped by the
    same rule, unmeasured.
```

### Fully labeled

Reads exactly as it does today. No regression on the existing path.

### The service section goes dark, and says why

Every chain row has `memo = None`, so every service row lands uncategorized. Rendering
that as one "No service identified — $1,592.05 (312 payments)" line is correct and
useless. When no transaction in range carries a memo, the breakdown is suppressed and
replaced with an explanation:

```
What they paid for
------------------
  This data carries no memo, so nothing here describes what was bought.
  On-chain transfers do not record which resource was purchased — that
  lives in the seller's request log, not on the chain.
```

This tells the user why the section is empty and what would fill it.

No user-facing string added by this release may advise on tax or accounting treatment.

## Testing

- **No test touches the network.** The fetcher is exercised against recorded JSON-RPC
  response fixtures.
- Fixtures are Sepolia-derived or hand-shaped and contain **no mainnet address**.
- Field mapping is covered per field, including that `amount_micro_usdc` passes through
  as an integer with no conversion.
- A transfer from the receiver back to a prior payer becomes `tx_type='refund'` with a
  positive amount.
- Bridged USDbC is excluded — a fixture containing it yields no transactions.
- Chunked range walking covers a range larger than one RPC request permits.
- A malformed log is skipped with a reason and counted, never silently dropped.
- The three report states (unlabeled, partially labeled, fully labeled) each render
  their correct wording, asserted on rendered output.
- The service section suppresses and explains when no transaction in range has a memo,
  and renders normally when one does.
- `ledger shape` output contains no precision or recall figure — asserted, because the
  staging depends on it.
- The pre-registered criterion renders its verdict for each of the three branches.

Every changed existing test carries recorded justification. A threshold quietly
loosened to make a failure disappear is the one thing this project does not do.

## Privacy

Real fetched batches land in a git-ignored directory. The only mainnet-derived artifact
that may enter git is a labeled measurement sample, and it gets an explicit privacy
review before it lands — or is address-anonymized with the mapping kept out of the
repo.

## Global constraints

Unchanged from v0.1c:

- Python ≥3.13. **Runtime dependencies MUST remain empty — stdlib only.** pytest
  dev-only.
- **Money is ALWAYS integers in micro-USDC. Never a float.** A refund is a positive
  amount with `tx_type='refund'`.
- Timestamps ISO 8601 UTC, `YYYY-MM-DDTHH:MM:SSZ`, zero-padded, TEXT.
- Nothing forced into a bucket; nothing silently dropped.
- No user-facing string may advise on tax or accounting treatment.
- `CALIBRATION_THRESHOLD = 0.95` and `MIN_VERDICT_SAMPLE = 20` unchanged.
- **Confidence is per-axis.** Service money must never join the payer axis's
  "Confidently identified" total.

## Definition of done

- [ ] `ledger fetch` retrieves real native-USDC transfers for a receiver on Base
      mainnet, writing the JSON shape `ingest` already reads
- [ ] `ingest` is unmodified; network access exists only in `fetch`
- [ ] Bridged USDbC is excluded explicitly
- [ ] Refunds are detected from reverse-direction transfers and stored as positive
      amounts with `tx_type='refund'`
- [ ] No float appears anywhere on the ingest path
- [ ] `ledger shape` reports structure and provably no precision or recall
- [ ] `ledger label` emits a human worksheet; the tool never assigns truth
- [ ] The independent-evidence rule is documented where a labeler will read it
- [ ] The criterion is committed **before** the labels are
- [ ] **The criterion is applied and acted on** — earns, does not earn, or insufficient,
      not deferred
- [ ] The report distinguishes the three calibration states, derived from coverage
- [ ] The service section suppresses and explains when no memo exists in range
- [ ] No test touches the network; no mainnet address is committed in a fixture
- [ ] README and `docs/sample-report.md` record what was fetched, the labeled sample
      size and coverage, and the verdict
- [ ] Full suite passes; every changed existing test has recorded justification

## Deliverable

The first honest statement about how this tool performs on money that actually moved:
a real dataset ingested end to end, a payer confidence claim either earned on
independently-labeled real transactions or explicitly marked uncalibrated, and a report
that no longer implies calibration it does not have.
